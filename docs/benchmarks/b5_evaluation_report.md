# Milestone B5 Evaluation Report: Controlled LLM-Assisted RAG Reranking Baseline

## 1. Executive Summary & Research Objective

### 1.1 Objective
The goal of **Milestone B5** is to evaluate whether a local, open-weight Large Language Model (LLM) can improve requirement-to-source-code trace ranking after conventional candidate retrieval, while operating under a strictly controlled, reproducible, and offline-compatible experimental protocol.

Specifically, B5 investigates:
> *Can an instruction-tuned local LLM acting as a zero-shot relevance reranker on top-20 BM25 lexical candidates improve Mean Average Precision (MAP) and early-rank precision (P@1, P@3, P@5) without accessing ground truth or fine-tuning?*

### 1.2 Key Findings Summary
1. **Consistent Early-Precision & MAP Improvement:** Reranking the top-20 BM25 candidate pool with local LLM relevance scoring (`qwen3.5:9b`, temperature $0$, `think=false`) consistently improved MAP and P@1 across all three benchmark projects:
   - **`sample_project` (Python):** MAP increased from **0.7030** to **0.8076** (+14.88% relative gain); P@1 increased from 0.7000 to 0.8000.
   - **`iTrust` (Java EHR):** Candidate-restricted MAP@20 increased from **0.3526** to **0.4404** (+24.91% relative gain); P@1 increased from 0.3524 to 0.5143.
   - **`eTour` (Java Tourism):** Candidate-restricted MAP@20 increased from **0.2523** to **0.3649** (+44.63% relative gain); P@1 increased from 0.4035 to 0.5789.
2. **Fixed Recall Ceiling:** B5 is strictly a retrieve-then-rerank pipeline. It re-orders candidates within the candidate pool generated by B1 BM25. Consequently, **Recall@20 is mathematically identical between BM25 and B5** (1.0000 on `sample_project`, 0.6335 on `iTrust`, and 0.5562 on `eTour`). B5 cannot recover any ground-truth target omitted by the candidate generator.
3. **Inference Latency Trade-Off:** While conventional BM25 retrieval requires milliseconds per query ($\le 0.1\text{s}$ total per dataset), zero-shot LLM candidate evaluation requires substantial inference compute (~60s per requirement query on local hardware, totaling ~3.42 hours across the benchmark suite).

## 2. Experimental Setup & Frozen Architecture

```
Requirement Text
      │
      ▼
┌─────────────────────────┐
│   Frozen B1 BM25        │  k1 = 1.5, b = 0.75
│   Candidate Generator   │  (Whole-corpus lexical match)
└───────────┬─────────────┘
            │
            ▼ Exactly top-20 source-code candidates
┌─────────────────────────┐
│   Prompt Formatter      │  Template v1.0.0
│   (Budget: 1,000 chars) │  Code snippet truncation (~250 tokens)
└───────────┬─────────────┘
            │
            ▼ Structured Zero-Shot Prompt
┌─────────────────────────┐
│   Local LLM Provider    │  Model: qwen3.5:9b
│   (Ollama, Temp=0)      │  think=false, num_ctx=8192
└───────────┬─────────────┘
            │
            ▼ Validated JSON Output: [{"candidate_id": ..., "relevance": 0..3}]
┌─────────────────────────┐
│   Deterministic Reranker│  Primary: LLM Score (3..0 desc)
│   & Tie-Breaking Policy │  Secondary: Original BM25 Rank (asc)
└───────────┬─────────────┘  Tertiary: Target ID (lexicographical asc)
            │
            ▼
   Final Reranked Trace Hypotheses
```

### 2.1 Frozen Hyperparameters & System Configuration
All parameters were frozen a priori and remained completely untouched during benchmark execution:

| Parameter | Value | Rationale / Protocol Constraint |
| :--- | :--- | :--- |
| **Backend** | Ollama local API (`127.0.0.1:11434`) | Standard, self-contained local inference execution |
| **Model** | `qwen3.5:9b` | Pre-installed local open-weight instruction-tuned model |
| **Temperature** | `0.0` | Greedy decoding for deterministic, reproducible scoring |
| **Thinking Mode** | `false` (`think=false`) | Disables chain-of-thought generation; enforces strict JSON |
| **Context Window** | `num_ctx = 8192` | Sufficient context for requirement + 20 truncated candidates |
| **Candidate Generator** | Frozen B1 BM25 (`k1=1.5, b=0.75`) | Identical retrieval implementation to frozen baseline B1 |
| **Candidate Pool Size** | Exactly `k = 20` | Frozen window budget; independent of final evaluation cutoff |
| **Relevance Scale** | Discrete integers `0, 1, 2, 3` | Heuristic rubric: 0 (Unrelated), 1 (Marginal), 2 (Related), 3 (Direct) |
| **Code Window Budget** | 1,000 characters per candidate | ~250 tokens per candidate; prevents context boundary overflow |
| **Prompt Template** | Version `1.0.0` | Fixed schema requiring strict JSON key matching |
| **Max Retry Limit** | `2` retries | Retries only on JSON parse errors; temperature remains $0$ |
| **Fallback Policy** | Preserve original BM25 order | If parsing fails after retries, preserve BM25 ranking and log fallback |

### 2.2 Deterministic Tie-Breaking Policy
Because LLM relevance scores are discrete integers in $\{0, 1, 2, 3\}$, multiple candidates within the 20-element pool frequently share identical scores. B5 enforces a strict, multi-stage deterministic tie-breaker:
1. **Primary Key:** LLM Relevance Score descending ($3 \rightarrow 2 \rightarrow 1 \rightarrow 0$).
2. **Secondary Key:** Original BM25 Rank ascending ($1 \rightarrow 20$).
3. **Tertiary Key:** Candidate Target ID lexicographical ascending (guarantees order stability).

### 2.3 Strict Ground-Truth Isolation
Under no circumstances did the retriever, candidate generator, prompt builder, or LLM access benchmark ground-truth labels during retrieval or reranking. All evaluation metrics were computed independently by the evaluation harness after candidate lists were serialized.

## 3. Evaluation Scope & Methodological Disambiguation

### 3.1 Disambiguating Full-Corpus vs. Candidate-Restricted MAP
A critical methodological distinction must be highlighted when interpreting B5 results against baseline B1:

- **Full-Corpus Baseline Evaluation (Official B1 Baseline):**
  In the official baseline reports (documented in `README.md`), B1 BM25 ranks **every artifact across the entire repository corpus** ($N = 226$ classes for iTrust, $N = 116$ classes for eTour). If a gold link appears at rank 35, it receives reciprocal rank $\frac{1}{35}$ and contributes to the average precision sum.
  - Full-Corpus BM25 MAP on `iTrust`: **0.3718**
  - Full-Corpus BM25 MAP on `eTour`: **0.2987**

- **Candidate-Restricted Evaluation (Top-20 Pool Evaluation):**
  In the B5 retrieve-then-rerank paradigm, the LLM is only supplied with candidates from the BM25 top-20 pool. Consequently, any gold-standard link that BM25 ranked outside the top 20 is not available to the LLM and receives a precision contribution of 0 within the 20-candidate evaluation scope.
  - BM25 candidate-restricted MAP@20 on `iTrust`: **0.3526**
  - BM25 candidate-restricted MAP@20 on `eTour`: **0.2523**

> **Important Methodological Note:** Comparing B5 LLM Reranking (evaluated on the top-20 pool) directly against the full-corpus BM25 MAP numbers (0.3718 / 0.2987) would conflate two different evaluation denominators and cutoffs. The proper controlled comparison evaluates **both B1 BM25 and B5 LLM Reranking over the identical candidate pool ($k=20$)**.

### 3.2 Candidate Recall Ceiling
Because B5 does not perform repository-wide retrieval, its maximum possible recall is bounded by the candidate generator's Recall@20:
$$\text{Recall@20}_{\text{B5}} \equiv \text{Recall@20}_{\text{BM25}}$$

- On `sample_project`: Recall@20 ceiling is **1.0000** (all 16 gold links are captured in the top 20).
- On `iTrust`: Recall@20 ceiling is **0.6335** (181 of 286 gold links captured in BM25 top-20). The remaining 36.65% of gold links cannot be retrieved by B5.
- On `eTour`: Recall@20 ceiling is **0.5562** (171 of 308 gold links captured in BM25 top-20). The remaining 44.38% of gold links cannot be retrieved by B5.

### 4.2 Benchmark Metric Analysis
- **Substantial Early-Rank Precision Gains:** On both external benchmarks, P@1 increased by over 40% (iTrust: 0.3524 to 0.5143; eTour: 0.4035 to 0.5789). This indicates that the LLM is particularly effective at promoting true positives from within the top 5–10 candidates to the absolute #1 rank.
- **MRR Improvement:** Mean Reciprocal Rank improved significantly (+24.5% on iTrust, +17.8% on eTour), reducing the rank position at which the first relevant artifact is encountered.
- **MAP Gains within Candidate Window:** The consistent MAP improvement across all three projects (+0.1046 on sample, +0.0878 on iTrust, +0.1126 on eTour) demonstrates that the instruction-tuned model possesses sufficient zero-shot code-reasoning capacity to separate relevant compilation units from lexical distractors.

### 5.1 Explicit Denominators & Reliability Rates
From the official execution logs, operational reliability rates are defined with exact numerators and denominators as follows:

1. **Initial JSON Parsing Success Rate:**
   - **Per LLM Call Denominator:** $\frac{\text{Successful First-Attempt Parses}}{\text{Total LLM Invocations}} = \frac{196}{205} = \mathbf{95.61\%}$
     *(196 successful initial parses out of 205 total LLM calls; the remaining 9 calls comprise 6 retry attempts and 3 exhausted failures across 3 queries).*
   - **Per Query Denominator:** $\frac{\text{Queries Succeeded on Attempt 0}}{\text{Total Requirement Queries}} = \frac{196}{199} = \mathbf{98.49\%}$
     *(196 queries succeeded without requiring any retry out of 199 total requirement queries).*

2. **Fallback Rate:**
   - **Total Queries Denominator:** $\frac{\text{Queries Requiring Fallback}}{\text{Total Requirement Queries}} = \frac{3}{199} = \mathbf{1.51\%}$
     *(Exactly 1 query per project required fallback out of 199 total executed queries).*
   - **Evaluable Queries Denominator:** $\frac{\text{Queries Requiring Fallback}}{\text{Evaluable Queries}} = \frac{3}{172} = \mathbf{1.74\%}$
     *(3 fallback queries out of the 172 evaluable queries contributing to ranking metrics).*

3. **Fallback Handling:**
   - When retries were exhausted (attempt 2 failed), the reranker deterministically preserved the candidate pool in its original BM25 order with relevance score 0, and tagged candidate metadata with `b5_fallback = true` to preserve complete auditability.

## 6. Threats to Validity & Research Limitations

While the results demonstrate clear empirical ranking gains for B5 on these datasets, several significant limitations and threats to validity must be recognized:

### 6.1 Construct Validity
- **Relevance Granularity:** The integer scale $\{0, 1, 2, 3\}$ is a coarse heuristic. While it differentiates obvious matches from irrelevant code, it lacks the resolution to distinguish between classes with complex cross-cutting architectural responsibilities.
- **Code Window Truncation:** Constraining candidate code snippets to the first 1,000 characters (~250 tokens) prevents context exhaustion, but it inevitably truncates large Java compilation units. Methods located deeper in a file are not visible to the LLM during scoring.

### 6.2 Internal Validity
- **Pretrained LLM Contamination Risk:** While `qwen3.5:9b` was not fine-tuned by TraceWise, open-weight models trained on web-scraped GitHub corpora may have encountered public academic datasets like iTrust or eTour during pretraining. Although prompt construction did not provide ground-truth hints, memorization cannot be entirely ruled out.
- **Dependency on Candidate Generator:** B5 is entirely dependent on B1 BM25. In domains where lexical vocabulary mismatch is severe (e.g., complex clinical terminology matching generic data structures), BM25 candidate recall ceiling remains a severe bottleneck (e.g., 55.6% recall ceiling on eTour).

### 6.3 External Validity
- **Limited Benchmark Scope:** The evaluation covers only three software projects (one synthetic Python microservice, two academic Java benchmarks). These results cannot be generalized to large enterprise repositories, multi-language monorepos, or dynamic scripting languages without further empirical replication.
- **Artifact Granularity Disparity:** `sample_project` evaluates granular method/function AST chunks, whereas `iTrust` and `eTour` evaluate entire Java compilation units (classes). The effectiveness of LLM reranking across diverse chunking granularities warrants deeper study.

### 6.4 Human-in-the-Loop & Productivity Considerations
- **Ranking Metrics $\neq$ Developer Productivity:** Improved offline MAP and P@1 demonstrate better ordering of hypotheses, but they do not prove that software developers will complete verification tasks faster or with fewer errors. In practice, high inference latency (~70 seconds per requirement) could disrupt interactive developer workflows unless asynchronous precomputation or smaller edge models are employed.
- **Need for Milestone B6:** Evaluating true software engineering utility requires interactive developer validation studies, which will be investigated under **Milestone B6**.

## 7. Reproduction Guide

The B5 benchmark can be inspected or reproduced via the following commands:

### 7.1 Inspecting Checkpoints & Precomputed Results
The benchmark summaries and per-query candidate ranking checkpoints are preserved locally:
- `experiments/results/b5_official_benchmark_summary.json`
- `experiments/results/b5_checkpoint_sample_project.json`
- `experiments/results/b5_checkpoint_itrust.json`
- `experiments/results/b5_checkpoint_etour.json`

To inspect these results interactively in the TraceWise Dashboard:
```bash
python -m tracewise.dashboard
```
Navigate to `http://127.0.0.1:8000`, select **B5 LLM Reranking**, and inspect candidate scores and LLM relevance assessments directly.

### 7.2 Running the B5 Unit & Offline Test Suite
To verify the prompt formatting, JSON parser, tie-breaker, and fallback mechanisms offline (using the deterministic mock provider):
```bash
pytest tests/test_b5_reranker.py -v
```

### 7.3 Reproducing Live Execution (Requires Ollama)
To rerun live inference using a local Ollama instance:
1. Ensure Ollama is running and model `qwen3.5:9b` is available:
   ```bash
   ollama list
   ```
2. Execute the B5 benchmark module:
   ```bash
   python -m tracewise.b5.benchmark --dataset sample_project
   ```
   *(Note: Executing the full iTrust and eTour benchmarks requires ~3.5 hours of continuous local GPU/CPU compute).*
